# 模型能力与兼容性

## 核心原则

兼容 OpenAI 请求格式不代表完整兼容 OpenAI 行为。工具调用、JSON Schema、流式、Embedding、超时、错误格式和模型名都需要分别实测。

## 探测顺序

1. 普通文本；2. 结构化输出；3. 工具调用；4. 流式；5. Embedding。

每项记录服务商、模型、非敏感 endpoint 标识、请求特性、HTTP 状态、结果、耗时和替代方案。不要记录 Authorization header 或密钥。

## JobCoach

先用已配置渠道完成最小文本调用，再针对结构化输出和 Tool Calling 做小实验。某能力不支持时，允许在 Java 应用侧解析/编排，不要假装供应商支持。

## 能力探测步骤

1. 固定一份不含隐私的最小请求和响应记录格式：provider、模型、特性、HTTP、耗时、结果类别、错误摘要和 fallback。
2. 先验证普通文本，再验证结构化输出、工具调用、流式和 Embedding；每项实验互相独立。
3. 给每项能力准备成功、超时、限流、非法响应和服务端不支持的样例。
4. 记录“OpenAI 兼容格式”和“行为真正兼容”的区别，不根据模型名称猜能力。
5. 将结论同步到能力矩阵，标注日期和实验版本；能力矩阵不写密钥、完整岗位内容或 Authorization。
6. 在应用中为未验证能力保留 fake/降级路径，并把实验失败转成可理解的错误状态。

## 复盘问题

1. 为什么同一个 endpoint 能通过文本实验，却不能直接推出 Tool Calling 可用？
2. 能力探测结果过期时，哪些测试需要重新运行？
3. 如果结构化输出不稳定，JobCoach 最小可交付方案是什么？
