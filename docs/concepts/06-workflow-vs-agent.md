# Workflow 与 Agent

## Workflow

由应用预先定义步骤和分支，行为可预测、容易测试，适合确定业务流程。

## Agent

模型在运行时选择下一步或工具，适合步骤无法完全预先固定但需要受控决策的场景。

## 选择原则

优先使用能完成目标的最简单控制方式。可固定的输入校验、调用模型、校验响应、保存记录应写成普通代码或 Workflow，不需要交给 Agent。

## JobCoach

分析报告生成后的固定保存流程应使用 Workflow。只有模型需要根据结果选择额外技能检索或追问时，才考虑 Agent 决策。

## 局限

“使用 Agent”不是质量目标。自由度增加会增加不可预测性、成本和测试负担。

## 决策流程与最小实验

1. 列出流程中的每一步：是否可预先定义、是否需要模型判断、是否有副作用、是否需要人工确认。
2. 将输入校验、模型调用、结构化校验、用户确认和保存先实现为普通代码/Workflow。
3. 只把“缺少信息时选择检索来源”作为候选 Agent 决策，并限制工具白名单和轮数。
4. 对比固定 Workflow 和 Agent 版本的测试数量、平均延迟、失败恢复、成本和解释难度。
5. 记录采用 Agent 的必要性证据；若没有证据，保留更简单的实现。

## JobCoach 取舍表

| 场景 | 默认方案 | 允许的模型自由度 | 原因 |
|---|---|---|---|
| 输入校验 | 普通代码 | 无 | 规则确定且必须稳定 |
| 匹配报告生成 | 一次模型调用 + Schema | 生成内容 | 需要模型理解文本，但结果要校验 |
| 保存准备任务 | Workflow + 用户确认 | 无 | 有业务副作用 |
| 缺少技能资料时检索 | 受限 Agent 候选 | 选择一个白名单工具 | 需要依据结果决定下一步 |

## 复盘问题

1. 如果去掉 Agent，用户价值是否下降，还是只少了一个技术名词？
2. 自由度增加后，新增了哪些测试和运维责任？
3. 哪些决策应该由产品/用户确认，而不是由模型替代？
