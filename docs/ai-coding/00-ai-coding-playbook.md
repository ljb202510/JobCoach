# AI Coding 全流程手册

AI coding 的目标不是提高一次生成的代码量，而是缩短反馈循环，同时保留人的判断、责任和验证能力。

## 标准循环

```text
探索 -> 上下文准备 -> 任务拆分 -> 方案评审 -> 小步实现
-> 测试/调试 -> diff review -> 记录/复盘
```

### 1. 探索

让 AI 先列目录、入口、现有约定、测试和 Git 状态。不要尚未读代码就要求重构。把事实、推断和未知分开。

### 2. 上下文准备

提供目标、用户场景、约束、相关文件、不可改区域、预期行为和验收命令。只提供足够上下文，不要把整个仓库文本塞进 Prompt。

### 3. 任务拆分

一个任务应能用一两个相关测试验证。先分离依赖升级、行为变化、重构和 UI 变化，避免难以定位回归。

### 4. 方案评审

要求模型说明备选、风险、受影响文件和验证方法。由人选择产品边界、权限、副作用和不可逆决策。

### 5. 小步实现

先声明将改哪些文件和范围；避免顺手重构。代码完成后检查是否遵循项目约定。

### 6. 测试与调试

先运行最快相关检查，再扩展测试。失败时读取完整错误、形成假设、做最小实验；不隐藏失败或降低断言来“让测试通过”。

### 7. Diff Review

逐项看行为、边界、异常、密钥、日志、依赖、测试和无关变更。AI Review 是辅助，不是批准。

### 8. 记录与复盘

记录决策依据、失败尝试、真实验证结果、未覆盖风险和下次可复用做法。

## 人与 AI 的职责

- AI 擅长快速搜索、总结、给候选设计、生成局部代码、提出测试和解释错误。
- 人负责确认需求、数据/权限边界、技术取舍、风险接受、验证是否充分和最终合并决定。
- 若 AI 缺少关键信息，应先询问或标记假设，不得把猜测写成事实。

## 使用 AI 的三个刻意动作

### 用“实习生式”而不是“搜索式”提问

把 AI 当成执行力强但不了解项目内部规则的协作者。每次任务至少说明背景、目标、约束、允许修改范围、不可接受的副作用和输出/验收格式。只问几个关键词，得到的通常只是通用答案；把真实上下文说清楚，才能让结果贴近项目。

### 在开始手工操作前先问“AI 能帮多少”

遇到重复整理、脚手架、测试样例、日志分析或文档同步工作时，先判断是否值得自动化；不适合自动化的任务也要明确原因。可以从每周自动化一个小的重复任务开始，但每次都要保留输入、输出和人工复核步骤，避免把节省时间变成隐性维护成本。

### 用真实世界反馈抵消模型的正向幻觉

模型的肯定不是质量证明。代码要经过测试和 Review，产品要经过真实用户或演示验收，方案要用实际约束和数据回测。把“模型说可行”记录为假设，把“测试/用户/线上指标证明”记录为证据；两者不能混写。

这三点来自外部经验文章的归纳，属于工作习惯建议，不是 JobCoach 已完成能力的声明。

## 外部文章中的九条 AI 使用原则

下面是“用 AI 的这三年”一文的内容整理。它们是作者的个人建议，我把它们翻译成适合 JobCoach 学习阶段的练习，不代表必须购买某个模型或接受文章中的效率判断。

### 1. 用足够好的模型做能力基线

文章提醒：普通模型的失败体验可能让人误判 AI 的上限。对学习项目，更稳妥的做法是先选择一个当前能合法使用、文档清楚、成本可接受的模型做基线，再比较替代渠道。记录任务类型、模型、Prompt、响应时间和错误，不要把一次好结果写成普遍能力。

### 2. 每周自动化一个重复任务

不要从“做一个全自动平台”开始。先找一个每周重复、输入输出稳定、失败可人工补救的任务，例如把测试结果整理成复盘模板、把模型能力实验转换成表格、检查文档链接。定义手工基线时间、自动化实现时间、维护成本和节省时间，连续运行几次后再决定是否扩大。

### 3. 从搜索式提问切换到实习生式协作

搜索式提问只给关键词，实习生式任务则说明背景、目标、限制、截止时间、受众、已有材料和期望格式。JobCoach 任务可以这样写：

```text
背景：当前只有 fake /api/matches，真实模型尚未接入。
目标：增加结构化输出适配，但保持 fake 回归集通过。
约束：不提交密钥，不修改数据库，不引入无关框架。
验收：合法/非法 JSON 各有测试，模型失败返回稳定错误。
输出：先列事实和未知，再给 3-6 条计划，最后报告文件和测试。
```

### 4. 形成“AI 能帮我吗”的触发器

开始重复劳动前暂停一秒，问“AI 能帮多少、需要什么输入、风险是什么、如何验收”。不是所有工作都要自动化；高风险、隐私密集或不可逆的动作可能只适合让 AI 提供草稿和检查清单。

### 5. 通过创造来学习

文章强调做出一个小工具比只收藏教程更容易形成反馈。对本项目，这意味着每学一个概念都绑定一个小产出：Prompt 对照实验、Fake gateway 测试、工具参数校验、错误状态演示或一页架构图。产出很小也可以，但必须能运行、解释或验证。

### 6. 警惕 AI 的正向幻觉

模型说“方案很全面”不是 Review 结论。把模型评价记为假设，把测试、用户演示、真实数据和代码证据记为验证。每次收到夸奖时追加一个反向问题：哪里可能错？什么证据能推翻它？最坏的副作用是什么？

### 7. 不要等准备完美再开始

文章建议用最小可行任务边做边学。工程上要加一个安全门：可以尽早开始，但先选 fake、只读或可回滚动作，不要用“先试试看”掩盖真实部署、删除和密钥操作。

### 8. 培养自己的判断与品味

AI 可以生成多个标题、方案、UI 或代码版本，但“哪个更适合用户、哪个更易维护、哪个证据更充分”仍需要人判断。训练方式是看优秀案例、写出好在哪里、自己做一个版本、对照差距，再把判断标准固化为 Review 清单。

### 9. 把省下的时间还给现实世界

效率不是让人永远在线。项目学习应安排明确的工作时段、停机点和复盘时间；自动化节省的时间可以用于真实用户访谈、面试准备、休息和与人交流。作者的生活观点不属于软件需求，但它提醒我们不要把 Token 消耗量当成产出指标。
