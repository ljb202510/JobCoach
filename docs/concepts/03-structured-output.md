# 结构化输出

## 定义

把模型结果映射成可由程序消费的数据结构，例如 JSON 对象或 Schema 约束响应。

## 为什么需要

业务需要稳定字段，而自然语言段落不适合直接驱动 UI、数据库和工具。

## 建议链路

```text
模型响应 -> JSON/Schema 解析 -> 字段校验 -> 业务规则校验 -> 使用
```

## 边界

JSON 可解析不代表语义正确；Schema 支持可能因供应商、模型和 API 参数而异；解析成功不能替代业务规则校验。

## JobCoach 用法

报告字段包括岗位要求、证据、差距、优先级和准备建议。分数范围、枚举值、列表长度和无证据表达由应用再次验证。

## 验证

构造缺字段、错误类型、非法分数、额外文本、空列表和矛盾内容测试；记录服务端实际支持的约束模式。

## 面试表达

说明结构化输出是模型响应契约，不是模型可信性保证，因此解析与领域校验必须分层。

## 学习步骤与最小实验

1. 先定义领域报告字段表：名称、类型、必填性、枚举、范围、来源和缺失行为。
2. 准备正常 JSON、Markdown 包裹 JSON、缺字段、类型错误、非法枚举、超范围分数和矛盾证据样例。
3. 分别测试语法解析、Schema 校验和领域规则校验，记录每种错误的响应 code。
4. 将模型 DTO 转换为领域对象，禁止把供应商的原始响应对象向 Web 层泄漏。
5. 统计一组样例的解析成功率、语义校验通过率和需要人工复核的比例。

实验验收：能够证明“可解析”与“可接受”是两个不同门槛，并有测试覆盖这两个门槛。

## 常见误区

- 看到 HTTP 200 或 JSON 可解析就当作业务正确。
- 只校验字段存在，不校验范围、证据、关联关系和业务状态。
- 为了让测试通过而放宽 Schema，掩盖模型输出漂移。

## 复盘问题

1. 哪些字段必须在服务端重新计算，不能由模型直接决定？
2. 结构化失败时是重试、降级到 fake、返回错误还是人工修复？
3. 如何用最小样例集捕获 Prompt 或模型升级带来的字段漂移？
