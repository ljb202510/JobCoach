# JobCoach 扩展需求规格说明书 —— 编写计划

## 1. 概述

为 JobCoach MVP 制定下一阶段（30 天路线）的**扩展功能需求规格说明书**：从第一性原理出发，推导出可拓展 MVP 的功能需求方向池，经多视角交叉评审收敛后，形成按 P0/P1/P2 分级、每条含用户故事/价值/依赖/验收的正式规格文档。

- 执行主体：TRAE（本会话）独立完成，不拉起 Codex CLI / Qoder 插件。
- 「三 agent 视角」以方法形式保留：每候选方向依次经过「需求/产品视角(Qoder)」「后端可落地性视角(Codex)」「编排/隐私/证据视角(TRAE)」三视角交叉评审，再由 TRAE 汇总定稿。
- 产出范围：**广覆盖方向池 + 分级**（覆盖持久化/历史、登录、简历上传解析、岗位导入、RAG、模拟面试、多 Agent 产品能力、流式、评测等全部候选方向）。

## 3. 提议的改动

### 3.1 新建文档（核心交付物）

`docs/product/12-extension-requirements.md`，标题「JobCoach 扩展功能需求规格说明书（下一阶段方向池）」。

文档结构（编写时按此填充）：

1. **目的与范围** — 与 `03-functional-requirements.md`（当前 MVP 规格）、`next-backlog.md` 的关系；本 doc 取代 next-backlog 的「方向清单」角色并补全规格。
2. **第一性原理与推导基准** — 公理 + 价值链条 + 双重目标约束。
3. **扩展方向总览** — 分级总表（方向 | P级 | 权重归属 | 一句话价值）。
4. **方向明细** — 每条方向固定字段：用户故事 / 第一性原理依据 / 核心价值 / 依赖 / 验收要点 / P级 / 权重归属(4:4:2) / 风险与边界。
5. **交叉评审结论** — 三视角评审记录、合并/剔除/降级理由、遗留争议。
6. **待用户确认事项** — 需用户拍板的开放问题（如「是否长期保存简历原文」等）。

### 3.2 第一性原理推导基准（写入 doc 第 2 节，作为各方向的推导根）

- 公理 1：用户根本问题 =「我适不适合这个岗位、还差什么、下一步做什么」——一切扩展都要回到缩短「识别差距 → 补足证据 → 可执行行动」的闭环，或降输入成本、升输出可信度。
- 公理 2：目标用户 = 软件工程学生/初级求职者，主攻 Java 后端 + AI 应用/Agent 方向。
- 公理 3：双重目标约束 4:4:2，方向必须能落到产品价值、AI coding 概念、Java 后端三者之一。
- 公理 4：可信度优先——每个输出可回溯到岗位/经历文本/通用规则，不造伪精确分，失败可解释可重试，不写伪成功。
- 公理 5：边界——不自动投递、不抓招聘网站（除非另行评估来源/平台约束）、不做复杂多用户（除非隐私评审）。

### 3.3 候选方向池（第一性原理推导，覆盖价值链各层，撰写时逐个过审）

分组与候选（最终以评审结果为准，可合并/剔除/降级）：

- 输入层（降成本）：简历/经历文件上传解析、岗位链接导入、历史输入复用。
- 分析层（升质量）：RAG 可信资料引用、多模型/渠道切换与降级、评测集与报告质量指标、流式输出。
- 行动层（把建议变成行动）：准备任务持久化 + 确认保存 + 跟进状态、面试题生成、模拟面试、任务提醒/进度。
- 长期使用层（跨会话）：登录与用户资料隔离、报告/计划历史查询、删除与隐私保留策略。
- 工程/AI 能力层（服务 4:4:2 中 AI coding 目标）：多 Agent 原生产品能力、Tool Calling 白名单扩展、Workflow→受限 Agent 升级、可观测性与成本记录。

### 3.4 交叉评审方法（写入 doc 第 5 节的依据）

每个候选方向依次过三视角，任一否决即裁定：

- 需求/产品视角（Qoder）：痛点真伪、用户故事是否可验收、是否与主线重叠。
- 后端可落地视角（Codex）：依赖/成本、是否可拆成可回滚小步、Java/Spring 生态可行性。
- 编排/证据视角（TRAE）：隐私/副作用、外部网络、是否触及「先停设计再实现」红线、能否写出 A/B 级验收证据。

裁决动作：合并重复方向 / 剔除伪需求 / 降级为候选 / 保留争议待用户拍板。
