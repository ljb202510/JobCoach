# Trae-JobCoach 扩展功能需求规格说明书（下一阶段方向池）

## 1. 目的与范围

本文档是 JobCoach MVP 之后、下一阶段（约 30 天路线）的**扩展功能需求规格说明书**。它从第一性原理出发，枚举可拓展 MVP 的功能需求方向，经多视角交叉评审收敛后，形成按 P0/P1/P2/候选 分级、每条含用户故事 / 依据 / 价值 / 依赖 / 验收要点 / 权重归属 / 风险与边界的正式规格。

与既有文档的关系：

- 当前 MVP 的功能规格保持不变，见 [03-functional-requirements.md](03-functional-requirements.md)（`00~11` 为当前 MVP 主规格，本文档顺延为 `12`）。
- [next-backlog.md](../plan/next-backlog.md) 是一张简表（P0/P1/P2/候选），本规格**取代其「方向清单」角色**：兼容其 P1/P2/候选 条目，补齐每条的用户故事、第一性原理依据、验收要点与三视角评审记录。
- 分级口径沿用 [PROJECT_GOALS.md](../plan/PROJECT_GOALS.md) 的 P1/P2 清单与 4:4:2 权重，不与之冲突。

本文档只写到「方向 + 规格」层级，不展开实现级设计；具体接口契约、错误码、模块拆分留给后续正式需求评审（阶段 1~3，见 [dev-workflow.md](../plan/dev-workflow.md)）。

## 2. 第一性原理与推导基准

### 2.1 公理

- **公理 1（根本问题）**：用户根本问题是「我适不适合这个岗位、还差什么、下一步做什么」。一切扩展必须回到缩短「识别差距 → 补足证据 → 可执行行动」的闭环，或降低输入成本、提升输出可信度。偏离此闭环的方向都不进入 P0/P1。
- **公理 2（目标用户）**：软件工程专业学生 / 初级求职者，主攻 Java 后端 + AI 应用 / Agent 方向。方向需落到这类用户真实高频场景。
- **公理 3（双重目标约束）**：每个方向必须能落到 4:4:2 三者之一——作品集产品（4）/ AI coding·概念能力（4）/ Java 后端（2），并说明会挤占哪部分已有时间。
- **公理 4（可信度优先）**：每个输出能回溯到岗位文本、经历文本或明确通用规则；不造伪精确分；失败可解释、可重试；不写伪成功记录。
- **公理 5（边界）**：不自动投递、不抓招聘网站（除非另行评估来源与平台约束）、不做复杂多用户（除非完成隐私评审）。

### 2.2 价值链条

```text
输入（降成本） → 分析（升质量） → 行动（把建议变成行动） → 长期使用（跨会话）
                                              ↑ 工程/AI 能力层贯穿支撑以上各层
```

五层对应本文档第 4 章的方向分组；每条方向标明它服务链条的哪一环。

## 4. 方向明细

以下每条方向按固定字段给出：用户故事、第一性原理依据、核心价值、依赖、验收要点、权重归属、风险与边界。

### 输入层

#### D1 简历/经历文件上传与解析（P2）

- **用户故事**：作为求职者，我希望上传 PDF/Word/Markdown 简历，自动转成可分析的经历文本，而不是手工粘贴。
- **依据**：公理 1/公理 2——降低输入成本是「降成本」侧最直接的环节。
- **核心价值**：减少录入摩擦，扩大可用人群；也是作品集产品的「文件处理」亮点。
- **依赖**：文件解析库选型（PDF/Word）、大小与类型校验、解析失败降级为手工粘贴。
- **验收要点**：上传合法文件可解析出文本并进入分析；超大/损坏/加密文件给出明确错误并可手工粘贴兜底；解析内容不落日志。
- **权重归属**：作品集产品（4）/ Java 后端（2，I/O、大小限制、字节校验）。
- **风险与边界**：解析精度受限；敏感简历原文的保留需先过 D14 隐私评审；不承诺简历自动改写。

#### D2 岗位链接/职位导入（候选）

- **用户故事**：作为求职者，我希望能粘贴岗位链接或从常见平台导入 JD，而非手动复制整段。
- **依据**：公理 1 降成本；公理 5 边界。
- **核心价值**：进一步降低输入成本。
- **依赖**：数据来源合法性评估、具体平台约束。
- **验收要点**：仅当来源与平台约束评估通过后才排期；先支持「链接贴入后抓取标题+文本」最小用例。
- **权重归属**：作品集产品（4）。
- **风险与边界**：涉及外部网络与平台反爬，属公理 5 红线，**降级为候选**，需独立评估后再入 P。

#### D3 历史输入复用与岗位模板（候选）

- **用户故事**：作为求职者，我希望能复用上次填过的经历文本，或套用岗位模板。
- **依据**：公理 1 降成本。
- **核心价值**：重复投递时快速起步，成本极低。
- **依赖**：D13 历史查询 或 本地浏览器的简单缓存。
- **验收要点**：能一键回填上次经历；不引入服务端持久化（可行时用浏览器本地存储）。
- **权重归属**：作品集产品（4）。
- **风险与边界**：属锦上添花，价值优先级低，保持候选。

### 分析层

#### D4 RAG 可信资料引用（P1 关键词检索 / P2 向量）

- **用户故事**：作为求职者，我希望每条准备建议都附上可核查的资料来源，而不是"看起来像真的"。
- **依据**：公理 4 可信度优先，RAG 是「升质量」的核心手段；也是 AI coding 目标（RAG 概念）的落地。
- **核心价值**：让建议可追溯、可核查；项目里落地一个真实 RAG 增量。
- **依赖**：可信资料来源的选取与评测；先最小化（关键词/规则检索），向量库为后续。
- **验收要点**：引用可回溯到来源；有检索 vs 无检索的对照评测，效果优于基线；不引入未经评测的资料源。
- **权重归属**：AI coding·概念（4）。
- **风险与边界**：资料来源可信度是前提，先确认来源再谈效果；先不做向量数据库（公理 5 / PROJECT_GOALS P2）。

#### D5 多模型渠道切换与降级（P1）

- **用户故事**：作为用户，当默认模型不可用或超预算时，我希望系统能切到备选渠道或降级到 Fake，而不是直接失败。
- **依据**：公理 4 失败可解释、可用；PROJECT_GOALS 已列「模型渠道切换」入 P1。
- **核心价值**：提升可用性与健壮性；落地「渠道切换」工程能力。
- **依赖**：稳定的 gateway 接口抽象、多个渠道的独立能力探测。
- **验收要点**：主渠道失败可切备选；无备选时可明确降级并提示 Fake 模式；切换不破坏 Fake/Real 回归集。
- **权重归属**：AI coding（4）。
- **风险与边界**：扩展渠道前先逐项验证结构化/工具/流式能力，避免「OpenAI 兼容」假设。

#### D6 评测集与报告质量指标（P2）

- **用户故事**：作为开发者/学习者，我希望有最小评测集和指标，能比较不同模型/提示词的质量。
- **依据**：公理 4 可信；AI coding 目标的「评测」环节。
- **核心价值**：让质量可比较、可回归，支撑 D5 与后续调优。
- **依赖**：稳定脱敏 fixtures 与样例、失败类别标注。
- **验收要点**：记录通过率与失败类别；新增改动可跑回归；样例全程脱敏。
- **权重归属**：AI coding（4）。
- **风险与边界**：先小后大，不追求学术级评测。

#### D7 流式输出（P1）

- **用户故事**：作为用户，我希望长报告边生成边显示，而不是长时间等待。
- **依据**：公理 1 降低"等待"体验；PROJECT_GOALS P1 含流式。
- **核心价值**：显著改善体感；落地 SSE/流式工程能力。
- **依赖**：模型流式能力验证、前端增量渲染、SSE 协议。
- **验收要点**：首 token 快速可见；中断/出错时保留已生成部分并可重试；不破坏非流式回归。
- **权重归属**：产品（4）/ Java 后端（2，SSE）。
- **风险与边界**：结构化报告与流式并存需评估（可先流式输出过程文本，最终落结构化结果）。

### 行动层

#### D8 准备任务持久化 + 确认保存 + 跟进状态（P1）

- **用户故事**：作为求职者，我希望确认后的准备计划能保存，下次打开仍能继续跟进任务。
- **依据**：公理 1 核心闭环的最后一个缺口——「把建议变成可执行、可跟进的任务」。
- **核心价值**：补全「分析 → 计划 → 跟进」完整产品闭环；落地 MySQL/MyBatis/迁移等 Java 后端核心能力。
- **依赖**：MySQL/Flyway 接入、Repository、用户确认流程、幂等键。
- **验收要点**：未确认不保存；重复确认不重复创建；重启后计划仍可查；删除能力见 D14。
- **权重归属**：产品（4）/ Java 后端（2，持久化）。
- **风险与边界**：先升级 05-domain-model 草图为正式 schema，再做迁移与集成测试；隐私保留策略先行。

#### D9 面试题生成（P1）

- **用户故事**：作为求职者，我希望系统根据我的差距生成可练习的面试题，而不是只有"去学习 X"的空泛建议。
- **依据**：公理 1 把差距转成可练行动；PROJECT_GOALS P1 含面试题生成。
- **核心价值**：让行动建议更具体、可直接执行。
- **依赖**：稳定的匹配报告结构、题目质量校验。
- **验收要点**：题目与岗位/差距可追溯；生成失败不冒充成功；可演示一轮生成。
- **权重归属**：产品（4）/ AI coding（4）。
- **风险与边界**：区分「题目生成」与「模拟面试」；先做静态题目，不引入对话系统。

#### D10 模拟面试（P2）

- **用户故事**：作为求职者，我希望围绕岗位和自身差距进行对话式问答练习，并获得反馈。
- **依据**：公理 1 行动层；PROJECT_GOALS P2。
- **核心价值**：把被动准备变成主动练习，是更强的产品差异化。
- **依赖**：D8/D9 的匹配与题目能力、对话状态管理、评价规则。
- **验收要点**：问答与反馈可重复演示；不泄露完整简历/岗位原文；有明确结束条件。
- **权重归属**：AI coding（4，多轮对话/状态）。
- **风险与边界**：对话系统成本与"幻觉"风险高，据公理 4 需可回溯评价。

#### D11 任务提醒/进度（候选）

- **用户故事**：作为求职者，我希望任务临期时收到提醒，或能标记进度。
- **依据**：公理 1 跟进闭环的增强。
- **核心价值**：提升长期使用粘性。
- **依赖**：D8 持久化、通知渠道（邮件/推送）、定时调度。
- **验收要点**：进度可标记；提醒可配置且不打扰。
- **权重归属**：产品（4）。
- **风险与边界**：涉及外部通知与定时任务，暂候选。

### 长期使用层

#### D12 登录与用户资料隔离（P2）

- **用户故事**：作为用户，我希望我的报告和计划只对自己可见，不被他人串读。
- **依据**：公理 1 长期使用前提；PROJECT_GOALS P2 登录权限。
- **核心价值**：支撑多用户真实使用。
- **依赖**：认证方案选型、会话隔离、D14 隐私策略。
- **验收要点**：A 用户看不到 B 用户数据；无认证的演示模式仍可用；权限边界经评审。
- **权重归属**：产品（4）/ Java 后端（2，安全）。
- **风险与边界**：做多用户前先完成隐私评审（公理 5）；可先做单机本地 profile 过渡。

#### D13 报告/计划历史查询（P1）

- **用户故事**：作为用户，我希望查看历史分析和过往计划，而非每次重来。
- **依据**：公理 1 跨会话跟进的前提；与 D8 同源持久化。
- **核心价值**：让"重新打开继续跟进"成为可能。
- **依赖**：D8 持久化能力、列表与详情接口。
- **验收要点**：历史可按时间列出；点击可回看报告；已删除项不再出现（见 D14）。
- **权重归属**：产品（4）/ Java 后端（2）。
- **风险与边界**：与 D8 一起规划，避免重复建表；历史原文的保留受 D14 约束。

#### D14 数据删除与隐私保留策略（P1）

- **用户故事**：作为用户，我希望删除历史或导出后，系统不再长期保留我的简历原文。
- **依据**：公理 4/公理 5 隐私红线；PROJECT_GOALS 已要求持久化前完成隐私评审。
- **核心价值**：合规与信任；是 D8/D12/D13 的前置闸门。
- **依赖**：保留周期与删除策略的明确决定（需用户拍板）。
- **验收要点**：删除后不可再查；日志仅脱敏摘要；保留策略有明确文档与测试。
- **权重归属**：产品（4）。
- **风险与边界**：是否长期保存简历/岗位原文是开放问题，见第 6 章。

### 工程/AI 能力层

#### D15 多 Agent 产品能力（P2）

- **用户故事**：作为用户，我希望系统能根据我的差距，自动选择"补充技能检索"还是"追问澄清"，而不是固定一条路径。
- **依据**：公理 1 动态决策；AI coding 目标（Agent 概念）；PROJECT_GOALS P2。
- **核心价值**：把产品从固定 Workflow 升级为有自主决策的一环；强作品集亮点。
- **依赖**：D4 检索、受限 Agent 循环、预算与停止条件。
- **验收要点**：仅在能证明带来用户价值时引入；有工具白名单与预算上限；失败可解释。
- **权重归属**：AI coding（4）。
- **风险与边界**：据公理 3 避免「为 Agent 而 Agent」；先证明价值再排期。

#### D16 Tool Calling 白名单扩展（P2）

- **用户故事**：作为系统，我希望在保持白名单与参数校验的前提下，安全地新增受控工具。
- **依据**：公理 4 可信/安全；AI coding 目标（Tool Calling 概念）。
- **核心价值**：受控扩展能力面，不破坏安全边界。
- **依赖**：工具 DTO 与校验框架、审计记录。
- **验收要点**：新增工具需白名单与参数校验；越权/附加参数被拒；执行有审计。
- **权重归属**：AI coding（4）。
- **风险与边界**：不暴露任意 Shell/SQL/文件系统。

#### D17 Workflow → 受限 Agent 升级（P2）

- **用户故事**：作为系统，我需要在"需要动态决策"的节点引入受限 Agent，其余仍保持固定 Workflow。
- **依据**：公理 1/公理 3；agent-design 已明确「先 Workflow，需要时再受限 Agent」。
- **核心价值**：在正确的位置引入动态性，控制成本与风险。
- **依赖**：D15/D16 能力、明确的 Workflow 边界划分。
- **验收要点**：固定环节仍固定；动态环节有预算、工具与停止条件；升级不破坏原有 Workflow 回归。
- **权重归属**：AI coding（4）。
- **风险与边界**：与 D15 合并交付或先 D16 后 D17，避免一次改动过大。
