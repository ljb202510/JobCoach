## 验证方案

### 安全边界

只使用环境变量中的 endpoint、model 和 key；输出中不得包含 key 或 Authorization。测试日志只保留脱敏请求摘要、状态码、耗时和错误类别。

### 阶段

1. 普通文本：最小 chat 请求，确认 endpoint、鉴权、模型名和基本响应。
2. 结构化输出：要求固定 JSON，再测试解析、缺字段和额外文本。
3. Tool Calling：声明一个无副作用只读工具，确认模型请求格式和工具选择响应。
4. 流式：确认 SSE/stream 行为和断开处理。
5. Embedding：确认模型名、维度、批量和失败格式。

### 结果表字段

```text
provider / model / base-url 标识 / date
request capability / status code / elapsed ms
result category / raw error category / fallback
```

“兼容 OpenAI”只作为待验证假设，不作为结果。

### 单次实验操作单

1. 选择一个不含真实简历、密钥或内部地址的最小输入，记录实验编号。
2. 从环境变量读取 endpoint、模型和 key；启动前确认日志不会打印请求头。
3. 只测试一个能力，保存状态码、耗时、脱敏响应摘要和错误类别。
4. 重复一次确认结果不是偶然成功；若不稳定，记录波动而不是强行归类为支持。
5. 运行本地解析/校验，区分网络成功、协议成功、结构成功和业务接受四个层次。
6. 将结果写入本文件和 `status-matrix.md`，同时记录 fallback 和下一步。

### 失败分流

| 现象 | 先检查 | 不要直接得出 |
|---|---|---|
| 401/403 | endpoint、环境变量、权限 | 模型不支持该能力 |
| 404/模型不存在 | 模型名和 provider 文档 | 所有文本调用都不可用 |
| 200 但解析失败 | 响应格式、Schema、额外文本 | provider 支持结构化输出 |
| Tool 无调用 | 工具描述、模型能力、请求格式 | 应用工具代码一定有问题 |
| 超时/限流 | timeout、配额、重试策略 | 模型质量差 |
