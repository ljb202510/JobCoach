# JobCoach 项目核心目标与协作约定

本文件是当前项目的目标基准。项目中文名为 **AI 求职教练系统**，英文名为 **JobCoach**。后续 Agent 或模型参与时，应先阅读本文件；若阶段计划与此处冲突，以用户最新明确决定为准，并同步更新本文档。

## 目标层级与权重

本项目的主线是 **AI coding 驱动的 MVP 开发**：我与 Codex/Agent 协作，从需求评审开始，经过优先级和模块拆分、方案设计、代码实现、Review、单元测试、整体联调和快速迭代，最终做出一个可运行的 JobCoach MVP。

因此，“AI coding”和“JobCoach 作品”不是两条分开的学习线：AI coding 是过程和方法，JobCoach 是这个过程最终交付的结果；概念学习则在真实开发遇到问题时按需引入并验证。

按用户明确给出的投入比例安排时间和验收重点：

| 目标 | 权重 | 具体含义 |
|---|---:|---|
| AI coding 主线与 MVP 交付 | 4/10 + 过程主线 | 通过真实任务完成需求评审、优先级排序、模块开发、代码 Review、单元测试、整体联调、快速迭代和最终交付；结果是可运行、可演示、可写进简历的 JobCoach MVP |
| 概念、Codex、Skills 与 AI 使用能力 | 4/10 | 在真实开发节点逐步学习和使用 Prompt、RAG、Skill、Tool Calling、MCP、Agent、Workflow 等概念，并熟悉 Codex 的 Plan、Thread、Review、测试和任务管理能力 |
| Java 后端支撑能力 | 2/10 | 学习支撑 MVP 交付所需的 Spring Boot、API、分层、测试、持久化和调试，不扩张成脱离项目的完整 Java 课程 |

时间和任务冲突时，优先保证前两项；Java 后端只做 JobCoach 主流程所必需的深度。

JobCoach 是 AI coding 主线的实际项目载体和最终交付物。任何时候不能为了快速生成代码而跳过需求评审、Review、测试、联调和复盘；也不能为了学习术语，把没有服务于当前迭代的 RAG、Agent 或工具硬塞进 MVP。

## 学习者与求职目标

- 软件工程专业大四，Java 基础一般，主力语言必须是 Java。
- 求职方向：Java 后端、AI 后端/全栈、Agent 开发。
- 通过真实项目训练代码阅读、调试、测试、设计、验证和 AI coding 工程工作流。
- 五天以一个连续 MVP 为主线：每一天都推进 JobCoach 的真实功能，同时在该功能需要时学习对应概念和 Codex 能力。
- AI coding 不等于让 AI 一次性生成全部代码；完整流程包括需求评审、优先级排序、模块拆分、上下文准备、方案设计、渐进实现、代码 Review、单元测试、整体联调、错误修复、文档同步和敏捷迭代。

## 产品目标

JobCoach 是一个面向求职者的 AI 求职准备系统，帮助用户分析目标岗位与个人经历之间的差距，并生成可执行的准备计划。

第一版核心主线：

```text
岗位描述 + 个人简历/经历
    -> 匹配分析
    -> 技能差距和证据说明
    -> 面试准备建议
    -> 生成准备任务（持久化在后续阶段）
```

## 五天内的 P0 交付

- 用户可以输入岗位描述和个人简历/项目经历；第一版不强制文件上传。
- 后端调用模型并返回结构化匹配报告：总体匹配、岗位要求、匹配证据、技能差距、风险和建议。
- 设计至少一个受控工具调用，例如保存准备任务计划；工具有白名单和参数校验，但五天 MVP 不执行持久化副作用。
- Vue 页面支持输入、提交、加载、结果和错误状态；报告、任务计划和执行步骤的持久化进入后续 30 天路线。
- 五天 MVP 只在当前请求内展示 Fake 报告，服务重启后不保留历史记录。
- 使用 fake AI gateway 完成核心业务测试；真实模型调用单独做能力探测。
- README 能指导启动、测试和演示，并明确已实现内容和局限。

## AI coding 主线的迭代闭环

每个功能都按同一条闭环推进，不把“学习概念”安排成脱离代码的独立课程：

```text
需求澄清
  -> 评审价值、风险和优先级
  -> 拆成模块与可验证任务
  -> 准备上下文和验收标准
  -> Plan/方案评审
  -> 小步编码
  -> 单元测试
  -> API/前后端整体联调
  -> Code Review
  -> 修复和回归
  -> 文档/状态同步
  -> 下一轮敏捷迭代
```

在闭环中按需插入概念：

- 需要稳定模型输出时学习 Prompt 和结构化输出；
- 需要外部知识时学习 RAG；
- 需要复用流程时创建 Skill；
- 需要外部能力时学习 Tool Calling 和 MCP；
- 需要动态决策时比较 Workflow 与 Agent；
- 需要熟悉 Codex 时使用 Thread、Plan、Review、测试和任务管理功能。

概念只有绑定到一个真实功能、实验或 Review 结论，才算完成学习。

## P1/P2 与非目标

- P1：MySQL 持久化、面试题生成、任务状态更新、岗位技能检索、最小 RAG、模型渠道切换和流式输出。
- P2：文件解析、模拟面试、多 Agent、向量数据库、Redis、登录权限、岗位抓取、异步工作流和生产部署。
- 第一版不做自动投递、招聘网站爬虫、复杂社交功能、自动修改简历文件或保证求职结果。

## 技术与安全约束

- Java 21、Spring Boot、LangChain4j、Spring `RestClient` 兜底、MyBatis-Plus、MySQL、Vue 3、TypeScript、Vite。
- 具体依赖版本先核对官方兼容性，再固定到构建文件。
- 模型服务只通过环境变量配置；不索取、记录或提交 API Key。
- OpenAI 格式兼容不代表结构化输出、工具调用、流式或 Embedding 均可用，必须逐项验证。
- 用户已安装 MySQL 8.4.9 并创建 `jobcoach`；Docker Desktop 仍为可选方案。数据库环境已具备不等于持久化功能已经接入，仍需迁移、Repository、集成测试和隐私评审。

## 教学与协作约定

- 每个任务说明目标、原因、预计耗时、改动范围和验收方法。
- 遵循：检查现状 -> 解释证据 -> 计划 -> 小步修改 -> 测试 -> diff/Review。
- 明确区分官方事实、作者经验和针对 JobCoach 的建议。
- 至少完成一次 Codex 计划/修改/测试/Review，一次项目级 Skill 实操，一次 MCP 概念或工具实操。
- 每天按验收标准复盘，完成后等待用户确认再进入下一天。
- 每个开发阶段都要记录 AI coding 流程：输入上下文、任务拆分、生成结果、人工检查、失败证据、修复方式、测试结果和复盘结论。

## 完成判据

JobCoach MVP 的核心流程可运行、结果和失败可验证、文档可复现；AI coding 的完整开发证据可回放；概念学习都能对应到代码、实验或 Review；所有未完成项和局限均被明确记录；学习者能用自己的话解释关键代码路径、框架选择、验证方式和主要取舍，才算五天交付完成。

## 任务决策顺序

任何新增任务按以下顺序判断，不允许先选技术再寻找用途：

1. 它是否直接改善岗位描述 + 经历 → 匹配 → 差距 → 准备任务主线？
2. 它服务 4:4:2 中哪一项，预计占用多少时间，挤掉什么已有任务？
3. 是否有用户/项目事实、源码、官方文档或实验结果支持？没有就标为假设。
4. 是否涉及隐私、权限、外部网络、不可逆副作用或需要用户决定？涉及则先停在设计/实验阶段。
5. 能否拆成一个可回滚的小步，并写出成功、失败、边界和回归验收？不能就继续拆分。

## 统一证据等级

| 等级 | 含义 | 文档写法 |
|---|---|---|
| A | 本仓库命令、测试或源码已验证 | 已验证 + 命令/文件 |
| B | 用户明确确认，但本仓库未复现 | 用户确认 + 待复现 |
| C | 官方文档/发布说明事实 | 官方来源 + 版本/日期 |
| D | 设计草案或外部作者经验 | 草案/作者经验，不得写成现状 |
| E | 未决定或暂缓 | 明确阻塞和下一步 |

## 每个阶段的最小交付包

阶段不能只交代码。至少包含：目标与非目标、受影响文件、决策记录、实现或实验、测试/验证输出、diff Review、局限和下一步。任何“已支持”表述都必须能指向其中一条 A 级证据。
