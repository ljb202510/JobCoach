# Codex、Skills、MCP 与 AI coding

Codex Desktop 负责探索、计划、Review 和复盘；VS Code 负责代码阅读、断点和前端编辑；终端负责构建、测试、Git diff 和 Docker。

## AI coding 全流程

1. 检查现状：读取目录、版本、配置、测试和 Git 状态。
2. 准备上下文：明确目标、约束、相关文件、不可修改内容和验收标准。
3. 拆解任务：把大目标分成可验证的小步，并标注风险。
4. 方案设计：让 AI 给出候选方案，人工选择边界和取舍。
5. 小步实施：一次只改一个清晰目标，修改前说明文件和范围。
6. 调试验证：运行最快相关测试，读取真实错误，不凭感觉修复。
7. Diff/Review：检查行为、边界、密钥、依赖、日志和测试缺口。
8. 记录复盘：保存决策、失败尝试、最终证据和可复用方法。

重点能力不是“会写提示词”，而是能控制上下文、验证 AI 输出，并在关键设计处做人工判断。

## Codex 的工作区与任务线

Codex 中的工作区（workspace）负责承载项目文件，Thread 负责承载一条具体任务的上下文。一个工作区可以有多个 Thread，但一个 Thread 应只推进一个明确目标。这样可以避免把需求分析、代码修改、文案编辑等无关任务混在同一上下文中，降低上下文污染和误改文件的风险。

开始任务前先确认：

- 当前工作区和 Git 状态是否正确；
- 本 Thread 的目标、允许修改范围和验收命令；
- 是否需要新建独立分支或工作树；
- 任务结束后需要保留哪些证据（测试输出、diff、Review 结论）。

Codex 的全局规则与仓库内 `AGENTS.md` 都属于约束来源。它们不能替代项目需求，也不能授权修改敏感配置；发生冲突时，以用户最新明确要求和仓库实际约定为准。

## Skills、Prompt 与 MCP 的边界

- Prompt 是当前对话中的一次性指令，适合临时说明目标、背景和输出格式。
- Skill 是可复用的流程包，通常是一个目录：`SKILL.md` 描述触发条件、步骤和验收方式，其他文件按需放参考资料、模板或脚本。Skill 应先暴露短的适用范围，再按需加载详细资料，这种“渐进式披露”可以减少上下文和 Token 消耗。
- MCP 是工具连接协议，解决 Agent 如何发现和调用外部能力；Skill 可以规定何时调用 MCP，但二者不是同一个层次。

一个最小 Skill 可以长这样：

```text
my-skill/
├── SKILL.md          # 必需：name、description、流程和验收
├── references/       # 可选：按需读取的资料
├── templates/        # 可选：输出模板
└── scripts/          # 可选：确定性辅助脚本
```

目录名应使用小写字母和连字符，`SKILL.md` 的元信息只描述真实适用范围；不要把所有背景一次性塞进主文件，也不要把需要人工批准的动作伪装成自动步骤。

本项目适合把重复且稳定的流程封装成 Skill，例如“检查现状 → 生成计划 → 小步修改 → 测试 → diff → 复盘”。Skill 不应把未经验证的产品宣传或隐含权限写成默认行为；涉及数据库、网络、部署和密钥时，必须保留人工确认点。

## 长任务的编排原则

对于跨多个模块的大任务，可以采用“研究/初案 → 独立评审 → 分阶段执行 → 测试与部署 → 线上检查 → 复盘”的流程。方案初稿不能直接视为可实施设计，至少要复核数据隔离、权限、失败恢复、迁移兼容和回滚路径。

长任务是否适合自动连续执行，取决于验收链路是否可靠：测试、CI、Review 和部署检查应先可重复运行；小任务优先使用短循环，不要为了追求无人值守而开启长目标模式。无论执行模式如何，人工仍负责范围、风险接受和最终上线确认。

## 文章中的 Codex 使用细节

参考文章把 Codex 的使用体验拆成了几个容易混淆的层次，这些经验可以转成项目纪律：

### 工作区负责文件，Thread 负责任务

文章中的工作区类似项目文件夹，Thread 是其中一条独立任务线。一个工作区可以同时承载学习资料、真实项目和沙盒，但同一个 Thread 不要上午改前端、下午处理表格、晚上再改文案。对 JobCoach 来说，可以按“产品方案”“后端主链路”“模型实验”“前端联调”拆 Thread；它们共享仓库文件，但每条线有自己的目标、上下文和验收。

建议每次新开 Thread 前先写：

```text
工作区：JobCoach
本 Thread 目标：只完成一个行为
相关文件：明确列出并先验证存在
不做什么：列出相邻但暂缓的功能
结束证据：测试、截图/响应、diff、复盘
```

### 大任务先用 Plan，执行时再切换

文章建议从零开始的大功能先进入 Plan 模式，让 Agent 产出方案、文件范围、阶段和验收，再决定是否执行。这个思路适合本项目的模型接入、持久化和 RAG，但不适合一个小 typo 或单个测试修复。

Plan 评审至少检查：数据隔离、权限、失败恢复、迁移兼容、回滚、测试时长和需要人工确认的副作用。计划通过不等于实现完成；执行阶段仍然按小步提交和测试推进。

### 前端任务先看真实页面，再决定是否继续

文章分享了一个实用判断：代码完成后先检查页面真实效果，再继续让 Agent 修正。迁移到 JobCoach，就是先用 fake API 验证输入、加载、报告和错误状态是否可用，再决定是否需要视觉迭代；不要只从代码 diff 推断用户体验。

### 并行 Thread 的边界

多个 Thread 可以并行，但并行数量受人的 Review 能力限制。适合并行的是互不冲突的只读研究、文档补充和独立测试；涉及同一 API、数据库迁移或共享配置时，应切分文件所有权或串行集成。线程越多，越需要统一状态矩阵和最终集成 Review。

### 设置与权限不能被经验文章直接照搬

文章提到定时任务、全局规则、Plan/Status、自动执行和高权限模式。对本项目的安全边界是：定时任务只用于明确授权的检查；全局规则和 `AGENTS.md` 不能替代项目需求；Full access/无人值守执行不能绕过密钥、权限、删除和部署确认。平台设置名称和模型档位会变化，应以当前产品界面和仓库安全规则为准。

### 模型版本和价格是时效信息

文章中出现的 GPT-5.3 Codex、GPT-5.6、Claude Fable 等版本、套餐、速度和价格属于作者发布时的个人体验，不写入 JobCoach 的兼容性结论。项目只记录本机实际探测到的 provider、模型、能力、耗时和错误。

## 一个可复用的 Codex 任务脚本

```text
1. 选择正确工作区，确认 git status 和当前 Thread 目标。
2. 小任务直接执行；大任务先 Plan，要求文件范围、风险、验收和回滚。
3. 让 Agent 先读代码和测试，复述事实、假设、未知。
4. 分阶段实施，每阶段运行最快相关测试并查看 diff。
5. 先检查真实 UI/API 行为，再决定后续修改。
6. 完整测试、Review、更新文档和状态矩阵。
7. 人工确认合并、部署、删除和其他不可逆动作。
```
