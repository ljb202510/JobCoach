# JobCoach 可复用开发流程

这份文件定义 JobCoach 从需求到交付的固定流程。每个功能迭代，包括后续所有增量开发，都按同一套阶段推进；`mvp-closeout-plan.md` 是这套流程的第一次实例。三工具（Codex / TRAE / Qoder）的分工与协作规则也写在这里，后续增量不需要重新对齐。

## 当前执行模式

当前 MVP 收口阶段只使用 Codex，由 Codex 负责实现、测试、联调、Review、回归和文档同步。下方「分阶段任务分工」「三工具协作规则」与并行规则暂不用于本轮；后续增量开发可按功能需要启用多 agent，并以当轮明确指令为准。

## Skill 使用规则

Skill 有两种用途：一是把项目中的重复流程封装成可复用能力；二是直接使用已安装的通用 Skill 来提升当前开发质量。每轮开始先盘点与任务相关的现有 Skill，向用户说明候选 Skill、适用场景和预期收益，再选择至少一个合适的 Skill 实际运行；不为凑数量强行使用无关 Skill。记录 Skill 名称、输入或触发方式、产出、验证结果和是否值得纳入项目流程。若 Skill 会改变代码或文档，仍遵守文件所有权、测试和 Review 规则。

## 十个阶段

每个阶段有固定输入、产出、完成门禁，以及一个主执行工具和一个独立复核工具。

| 阶段 | 输入 | 产出 | 门禁 | 主执行 | 复核 |
|---|---|---|---|---|---|
| 0 上下文与基线 | 仓库（冷启动才读目标/状态矩阵） | 基线 before 快照 | 三条基线命令通过；冷启动才需锁定唯一边界 | TRAE | 用户 |
| 1 需求评审 | 用户问题 | 用户故事、验收样例、非目标 | 价值、边界、验收均可验证 | Qoder | TRAE |
| 2 优先级排序 | 需求 | P0/P1/P2 清单 | 本轮只扩一个行为边界，其余进 backlog | Qoder | 用户 |
| 3 方案与接口设计 | P0 需求 | 接口契约、错误码、回滚点 | 方案与契约先于代码改动 | Qoder | Codex |
| 4 小步实现 | 方案 | 可回滚的代码改动、概念证据 | 一次只改一个可回滚小步 | Codex 后端 / Qoder 前端 | 对方 |
| 5 单元测试 | 实现 | 成功、输入错、依赖错、边界四类用例 | `mvn test -q` 通过 | Codex | TRAE |
| 6 整体联调 | 前后端、真实模型 | API + 前端 + 真实模型闭环结果 | Fake 与 Real 各自有独立证据 | TRAE | 用户 |
| 7 Code Review | diff | 契约、异常、脱敏、依赖、文档发现清单 | 记录至少一个有效取舍和一个发现 | Codex | Qoder |
| 8 修复与回归 | Review 发现 | 最小修复、回归结果 | 只修最高优先级，不改断言掩盖 | Codex | Qoder |
| 9 交付与复盘 | 全部证据 | 可演示产物、简历证据、backlog | 每项能力有 A/B 级证据 | TRAE | 用户 |

阶段顺序是固定的，但单轮的深度根据功能大小伸缩：一个 P0 功能可能占满全部 10 个阶段，一个只改一行文案的增量也可能只用 0、4、5、7、8 五个阶段。复用的是这份阶段清单和门禁，不是固定的时长。

## 分阶段任务分工（多 Agent 默认分工）

这是后续增量开发的多 Agent 默认分工。本轮 MVP 收口把它坍缩为 Codex 一人执行（见 `mvp-closeout-plan.md`），下表不用于本轮。

### 角色速查

| 角色 | 定位 | 典型交付物 |
|---|---|---|
| Codex | 后端实现与质量（终端 CLI） | 后端代码、单测、`/review`、git、回归 |
| Qoder | 需求/方案与前端（IDE 插件） | 需求、接口契约、前端代码、交叉复核 |
| TRAE | 编排、浏览器与证据（本环境） | 上下文编排、浏览器联调、Skill/MCP/RAG 证据、README/简历/演示、协作记录 |
| 用户 | 拍板与验收 | 优先级唯一权威、隐私/副作用/外部决策、肉眼视觉确认 |

表中「负责人」是主执行，「辅助」只帮忙、不得改负责人名下文件，「复核/确认」独立看结果。

### 阶段 0：上下文与基线

按"上下文是否新鲜"分两种跑法：三条命令每次必做；读文档、锁边界只在冷启动（隔了很久，或换新 Agent 接手）时才做。

**每次必做**

| 具体任务 | 负责人 | 辅助 | 复核/确认 |
|---|---|---|---|
| 跑 `git status --short`、`mvn test -q`、`npm run build`，取得 before 快照 | Codex | — | TRAE 记录 |

**冷启动 / 换 Agent 接手才做**

| 具体任务 | 负责人 | 辅助 | 复核/确认 |
|---|---|---|---|
| 读目标/状态矩阵/仓库结构，锁定唯一行为边界 | TRAE | Codex | 用户拍板 |
| 本轮目标 + 基线事实清单 | TRAE | — | 用户确认 |

### 分工与并行的关系

这张表回答"谁做什么"，`## 并行与串行` 回答"谁和谁能同时做"。两者叠加使用：先按本表确定每个任务的负责人，再按并行规则判断哪些任务能重叠、哪些必须串行（集成、回归、最终验收恒为串行，由主 Agent 收口）。

## 三工具协作规则

- 单一所有权：一个文件或模块同一时刻只属于一个主执行工具。跨边界改动先写接口契约，再由集成方（通常是主 Agent）合并，禁止交叉修改不属于自己的文件。
- 交接卡：主执行开工前写一张卡片，写明目标、允许触碰的文件、验收命令；结束时汇报动过的文件、命令结果、遗留风险。
- 交叉复核：代码由非作者工具 Review；浏览器、视觉这一类需要人眼确认的状态交给 TRAE 的浏览器自动化。
- 冲突仲裁：接口或所有权冲突由主 Agent（你本人或 TRAE）裁定，先记录再改。
- 密钥与隐私：密钥只从环境变量读取；日志不得出现简历全文、岗位全文或上游 Authorization。

## 并行与串行

阶段不是全部首尾相接。有些阶段可以重叠执行，前提是它们互不触碰同一批文件、且只依赖已经写死的接口契约。并行压缩墙钟时间，但不减少总工作量，还增加了集成和 Review 的收口成本。

判断规则只有一条：两个任务不碰同一批文件，又只依赖已冻结的契约，就可以并行。

| 任务对 | 能否并行 | 依赖前提 |
|---|---|---|
| 真实模型探测（Codex）∥ 前端联调（TRAE） | 能 | `POST /api/matches` + `MatchReport` 已冻结 |
| 后端单测（Codex）∥ 前端收口（Qoder） | 能 | 前后端目录隔离 |
| Skill / MCP / RAG 证据（TRAE）∥ Code Review（Codex） | 能 | TRAE 不碰后端代码 |
| 需求评审 → 实现 | 串行 | 方案是实现的输入 |
| 集成、回归、最终验收 | 串行 | 主 Agent 收口 |

现实形态是两路真并行加串行点评审：Codex 在终端跑后端（可后台运行），TRAE 同时做前端或概念证据，Qoder 在需求评审、方案、交叉 Review 这些串行节点介入——而不是三路同时铺开。

学习代价也要算进去：并行中某一路你没亲手跟进，那条路上的概念学习深度会打折。学习型迭代宁可在关键路上串行或独自盯紧，也别为了"看起来并行"把学习稀释掉。

## 概念到真实节点的映射

每个 AI 概念要么在开发流程里被使用，要么落地成项目能力，两者至少要有一条 A 或 B 级证据，否则不单独安排时间。

| 概念 | 开发流程中的用法 | 项目里的落地 | 负责工具 | 证据形式 |
|---|---|---|---|---|
| Prompt 与结构化输出 | 设计 `RealAiGateway` 的 system prompt 与 JSON schema | 匹配报告的 JSON 契约 | Codex | fence、缺字段、非法 JSON 单测 |
| Tool Calling（工具调用） | 设计受控工具的参数与白名单 | `PreparationPlanTool` 只生成准备计划预览；保存需另行确认 | Codex | 白名单校验测试、无副作用验证 |
| Skill | 先使用已安装 Skill 优化当前任务，再把稳定的项目步骤封装成项目级 Skill | 探索、计划、测试、Review、记录 Skill | 当前由 Codex 执行；后续可由指定 agent 执行 | Skill 选择理由、试运行结果和复用判断 |
| MCP | 用 MCP 工具做只读验证、浏览器自动化 | 浏览器联调、外部数据只读 | TRAE | MCP 工具输入与结果记录 |
| Workflow 与 Agent | 方案设计时判断固定流程还是自主决策 | `MatchAnalysisService` 的编排边界 | Qoder / Codex | 决策记录与测试 |
| RAG | 用可信资料做建议来源的对照 | 准备建议的可核查引用 | TRAE / Qoder | 检索与无检索对照 |
| Codex Plan / Thread / Review / 测试 / 任务 | 后端实现的全部过程能力 | 不落地为产品，作为协作过程能力 | Codex | 线程、Plan、`/review` 记录 |

这张表是增量开发时的速查：新功能进来后，先问它触及了表里哪几个概念，再决定要不要补对应证据。

## 证据等级

沿用全局证据等级，任何"已支持"的表述都要能指到一条 A 级证据：

| 等级 | 含义 | 写法 |
|---|---|---|
| A | 本仓库命令、测试、源码已验证 | 已验证 + 命令/文件 |
| B | 你确认过，但仓库未复现 | 用户确认 + 待复现 |
| C | 官方文档事实 | 官方来源 + 版本/日期 |
| D | 设计草案或作者经验 | 草案，不写成现状 |
| E | 未决定或暂缓 | 阻塞与下一步 |

## 停止条件

出现配置缺失、接口冲突、测试失败、敏感信息泄漏、工具文件冲突，或写不出可验证的验收条件时，暂停扩展范围，先记录证据、修复或明确阻塞，再进下一阶段。
