# Agent loop

## 定义

Agent loop 是反复进行“观察当前状态、决定下一步、执行动作、读取结果”的控制循环，直到完成、失败或达到预算。

```text
目标/状态 -> 决策 -> 工具动作 -> 观察结果 -> 更新状态 -> 决策或停止
```

## 关键控制

设置最大轮数、超时、工具白名单、预算、停止条件和失败状态。每轮保存可追踪步骤。

## 与单次调用的差异

单次模型调用返回答案；Agent loop 允许模型依据工具结果继续决策，因此更灵活，也更难预测和验证。

## JobCoach 用法

第一版可以把“分析 -> 生成计划 -> 保存计划”实现为受限循环，或固定 Workflow；只有确实需要模型基于工具结果再次决策时才引入自由 Agent loop。

## 局限

循环会放大延迟、成本和错误；工具结果可能不完整；必须保留可停止和人工确认机制。

## 学习步骤与最小实验

1. 先把 JobCoach 的分析流程写成固定状态机：received、analyzing、review_required、completed、failed。
2. 为每个状态定义允许动作、输入、输出、最大等待时间和停止条件。
3. 再增加一个受限决策：只有报告缺少技能证据时，Agent 才能选择一次检索工具。
4. 设置最大轮数、总超时和预算；模拟工具返回空结果、错误和相互矛盾的结果。
5. 重启进程后读取执行状态，验证不会因为内存丢失而无限重复或跳过确认。

实验验收：能展示一次成功循环、一次达到预算停止、一次工具失败和一次人工确认暂停，并且每轮都有记录。

## 常见误区

- 把多轮 Prompt 或自动重试误称为 Agent loop。
- 没有预算、最大轮数和停止条件，依赖模型“自己知道什么时候结束”。
- 为了展示 Agent，把本可固定的业务流程交给模型自由决定。

## 复盘问题

1. JobCoach 哪一步真的需要运行时决策？固定 Workflow 能否替代？
2. Agent 的观察状态是否足够，是否包含过多敏感历史？
3. 如何向用户解释“暂停等待确认”而不是显示成系统卡死？
