# RAG

## 定义

Retrieval-Augmented Generation：先从外部知识源检索相关内容，再把内容作为上下文交给模型生成回答。

## 最小流程

```text
数据准备/切分/索引 -> 查询 -> 检索 -> 组装上下文 -> 生成 -> 检查引用/相关性
```

## 常见组成

文档解析、chunking、Embedding（或关键词索引）、向量/全文存储、检索、重排、上下文组装和评估。

## JobCoach 用法

后续可检索岗位技能说明或用户自己的项目材料。第一版先验证核心匹配流程，不因追求 RAG 而引入向量数据库。

## 局限与验证

RAG 只能提供可能相关的材料，不能保证检索召回正确，也不能保证模型忠实引用。测 Recall、引用正确性、无命中时的拒答，以及过期/冲突资料处理。

## 学习步骤与最小实验

1. 建立一组小型公开资料，给每个文档记录来源、版本、更新时间和权限。
2. 先实现关键词检索基线，记录查询、候选数量、Top-K、命中率和延迟。
3. 再尝试 Embedding 检索或重排，只改变一个变量，避免无法解释效果来源。
4. 将检索片段带上来源标识、文档版本和边界；超过上下文预算时按规则裁剪。
5. 用问题集测试相关性、无命中、相似误命中、冲突版本、过期资料和敏感资料隔离。
6. 要求模型引用片段；人工核对引用是否真的支持结论，而不是只看格式像不像引用。

实验验收：至少有“无 RAG 基线”和“有 RAG 版本”的对照记录；如果质量没有稳定改善，文档中明确写出不采用的原因。

## JobCoach 的边界

岗位匹配的第一版可以只使用用户提供的岗位和经历，避免引入过时或未经授权的外部技能知识。后续若检索岗位技能库，必须处理来源版本、地区差异、岗位重复和用户删除请求。

## 复盘问题

1. 召回错误和生成错误分别发生在哪一层？如何区分？
2. Top-K 越大是否一定更好？它会带来哪些上下文和延迟成本？
3. 没有检索命中时，系统应该拒答、追问还是使用通用知识？
