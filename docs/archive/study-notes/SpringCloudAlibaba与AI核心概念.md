## 0. 一句话速答（先把你导师的问题答上）

- **Spring Cloud Alibaba**：一套基于 Spring Cloud、由阿里巴巴主导开源的「微服务全家桶」，把微服务开发里最常用的组件（注册发现、网关、限流、分布式事务、消息等）按统一规范集成好，开箱即用。
- **Nacos**：全家桶里的「**服务注册与发现中心 + 配置中心**」。负责回答两个问题：①别的服务在哪里、怎么找到它；②所有服务共用的配置怎么统一管理、改了不用重启。
- **Gateway**：全家桶里的「**API 网关**」。是所有外部请求进系统的**唯一入口**，负责路由转发、鉴权、限流、跨域等。

它们是这样串起来的（后面第 1.4 节展开）：

```
客户端请求
   │
   ▼
Gateway（API 网关：统一入口，先鉴权/限流/跨域）
   │
   ├──向 Nacos 查询"我要调的服务有哪些实例、在哪个地址"
   ▼
微服务 A ──(通过 Nacos 找到并调用)──▶ 微服务 B
   │                                    │
   └──配置统一从 Nacos 配置中心拉取────▶  │
                                    (Sentinel 限流熔断 / Seata 分布式事务 / RocketMQ 异步消息)
```

一句话记法：**Gateway 是"大门入口"，Nacos 是"通讯录+保险柜(配置)"，剩下的是"后台干活的人"。**

# 第一部分：Spring Cloud Alibaba 是干啥的

## 1.1 先懂背景：为什么微服务需要这么多组件

早期系统是**单体应用**：一个工程、一个包、一次部署，代码都在一起。团队小的时候没问题，但大项目会出现：代码太庞大、改一处全重新部署、某接口疯狂被打却拖垮整个系统、几十个人改一个仓库天天冲突。

于是拆成**微服务**：把原来一个大应用，按业务拆成很多个独立的小服务（订单服务、库存服务、用户服务……），各自独立开发、独立部署、独立伸缩。

但一拆开，麻烦就来了：

| 拆出来的问题 | 谁来管 |
| --- | --- |
| 服务地址写在代码里，服务一换地址全挂 | 服务注册与发现（Nacos） |
| 每个服务都有一堆配置，改一处要重启一批 | 配置中心（Nacos） |
| 客户端到底该访问哪个服务的哪个地址 | API 网关（Gateway） |
| 服务 A 要调用服务 B，怎么调最简单 | 服务调用（OpenFeign） |
| 某个接口流量突增，别拖垮整个系统 | 限流熔断（Sentinel） |
| 一个操作要同时改多个库，怎么保证都成功 | 分布式事务（Seata） |
| 两个服务要异步解耦，互相不等待 | 消息队列（RocketMQ） |

微服务框架（Spring Nordic 对齐）解决的就是：把这些能力**统一、标准化**地交给开发者，让大家不用自己造轮子。

## 1.2 Spring Cloud 和 Spring Cloud Alibaba 是什么关系

- **Spring Cloud**：Spring 官方出的**一套微服务"规范/约定"**。它本身不实现全部功能，而是定义了一套标准化的接口和用法。
- **Spring Cloud Alibaba**：**基于这套规范、由阿里落地的一组组件**。它用 Nacos、Sentinel、Seata、RocketMQ 等成熟组件，把 Spring Cloud 规范里"注册发现、配置、限流、事务、消息"这些位置填上实现；同时补了一些阿里特色的东西。

一句话：**Spring Cloud 是"规矩"（接口规范），Spring Cloud Alibaba 是"干活的组件包"（实现）**。你工作中基本上接触的就是 Spring Cloud Alibaba 这一套实际运行的组件。

> 需要澄清：**Gateway 是 Spring Cloud 官方的组件，不属于 Alibaba**。但因为同一个微服务体系里它们常一起用，导师把话匣子打开时通常会连着问，所以一并放这里讲。

## 1.3 全家桶组件盘点（先记这几个就够应付导师）

| 组件 | 中文俗称 | 它是干啥的（一句话） | 生活类比 |
| --- | --- | --- | --- |
| **Nacos** | 注册中心 + 配置中心 | 管服务发现和配置管理 | 通讯录 + 集中保险柜 |
| **Gateway** | API 网关 | 所有请求的统一入口 | 小区大门 + 门卫 |
| **OpenFeign** | 声明式远程调用 | 服务之间互相调用，像调本地方法一样 | 对讲机 |
| **LoadBalancer** | 负载均衡 | 多个实例里挑一个来调用 | 分配客流 |
| **Sentinel** | 限流熔断 | 流量过大限流、坏人直接短路降级 | 保险丝 / 限流闸 |
| **Seata** | 分布式事务 | 多个库同时改，保证要么都成要么都失败 | 一揽子交易 |
| **RocketMQ** | 消息队列 | 服务间异步解耦、削峰 | 快递驿站 |

## 1.4 一次业务请求怎么穿过这套体系

假设前端要"查订单明细"，背后其实要调订单服务 + 库存服务等多个服务：

```
① 前端请求 → Gateway
② Gateway 验证身份(Token/Cookie)、判断要不要限流、处理跨域
③ Gateway 向 Nacos 问：查"订单服务"的**调用地址**有哪些
④ Nacos 返回一份可用的实例列表（可能好几个，各在不同机器/端口）
⑤ Gateway 把请求路由转发到其中某个订单服务实例（LoadBalancer 在挑）
⑥ 订单服务要调库存服务时，同样通过 Nacos 找到库存服务地址（OpenFeign 发起调用）
⑦ 各服务启动时，都把自己的配置（端口、数据源、中间件等）从 Nacos 配置中心拉下来
⑧ 过程中 Sentinel 兜底限流熔断；若跨多个库，Seata 保证事务一致
```

**结论：Gateway 在入口，Nacos 在"找人"和"发配置"，其余组件在背后做支撑。**

## 1.5 版本快照（写对版本，避免被导师纠正）

Spring Cloud Alibaba 的版本和 Spring Boot / Spring Cloud 有严格对应关系，装错版本会直接起不来。当前（2026 年）概览：

| Spring Cloud Alibaba | 配套 Nacos | 配套 Sentinel | 配套 Seata | 适用 Spring Boot |
| --- | --- | --- | --- | --- |
| **2025.1.0.0**（最新） | 3.1.1 | 1.8.9 | 2.5.0 | Spring Boot 3.x 系 |
| 2025.0.0.0 | 3.0.3 | 1.8.9 | 2.5.0 | Spring Boot 3.x 系 |

- Nacos 版本已到 **3.2.4**（2026-08 发布），本身也定位成"易构建 AI Agent 应用的动态服务发现、配置管理和 AI 智能体管理平台"。
- 更老的 Spring Boot 2.x 项目用的是 Spring Cloud Alibaba 2021/2022 系（Nacos 1.x/2.x），**你本机项目可能是 Spring Boot 2 还是 3，要看 `pom.xml` 实际用的版本**，不要想当然。

> 参考：[Spring Cloud Alibaba 官方版本说明](https://sca.aliyun.com/docs/2025.x/overview/version-explain/)、[Nacos 官网](https://nacos.io/)。IDE 里看项目 `pom.xml` 里 `spring-cloud-alibaba-dependencies` 的版本号最准。

# 第二部分：Nacos 到底干啥

## 2.1 它对内官方定位就是"双面角色"

Nacos = **Na**ming and **Co**nfiguration **S**ervice，即「命名服务 + 配置服务」：

1. **服务注册与发现**（注册中心）—— 解决"服务在哪、怎么找到别的服务"
2. **配置中心** —— 解决"共用配置怎么统一管理、热更新"

## 2.2 注册中心：它怎么"找人"

**流程**：
- 每个微服务启动时，主动向 Nacos 报到：`我叫订单服务，跑在 192.168.x.x:8081`（注册）。
- 要调别人的服务时，先向 Nacos 查：`订单服务有哪些实例？` 拿到一份可用地址列表（发现）。
- Nacos 通过**心跳/健康检查**判断每个实例是否还活着，死了就从列表里剔除。

**解决的痛点**：以前你好不容易把别的服务地址写死在自己配置里，结果它换机器/加实例/挂了一台，你就得重启；有了注册中心，**地址是动态的，谁活着就调谁**。

**跟导师讲就一句话**：`Nacos = 班级通讯录`。服务像同学一样报到，别的服务查一下就知道该找谁、对方还活着没。

**典型配置（认得就行）**：
```yaml
spring:
  cloud:
    nacos:
      discovery:            # 注册中心
        server-addr: 192.168.31.100:8848
        namespace: dev      # 命名空间，隔离环境/部门
  application:
    name: order-service     # 注册到 Nacos 的服务名
```

## 2.3 配置中心：它怎么"发配置"

**流程**：
- 把各服务共用的配置（数据源、中间件地址、开关、降级阈值……）集中放到 Nacos。
- 服务启动时从 Nacos 拉取；你改了配置后 Nacos **动态推送给运行中的服务，不用重启**。

**解决的痛点**：散落在每个服务的 `application.yml` 里的配置，环境一多（dev/test/prod）就混乱；改一处要重启一堆服务。配置中心把这些统一收口，还支持**多环境隔离**。

**跟导师讲就一句话**：`Nacos = 集中保险柜`。配置放里面统一管，改完热更新，不用一台台去改重启。

**典型配置**：
```yaml
spring:
  cloud:
    nacos:
      config:               # 配置中心
        server-addr: 192.168.31.100:8848
        file-extension: yaml
# 具体配置项用 Data ID（如 order-service.yml）从 Nacos 拉取，可动态刷新
```

## 2.4 三个高频术语（报上去显得专业）

| 术语 | 通俗理解 |
| --- | --- |
| **namespace / 命名空间** | 把不同环境/租户隔离（dev / test / prod 各一个），互不干扰 |
| **group / 分组** | 同一环境里再分小组（如按业务域） |
| **Data ID** | 某一条配置的名字，如 `order-service.yml` |
| **实例 / 集群** | 一个跑着的服务 = 一个实例；多实例组成集群 |

# 第三部分：Gateway 到底干啥

## 3.1 定位：所有外部请求的统一入口

微服务是个"楼盘"，里面住着很多服务（订单、库存……）。如果客户端绕过门口直接敲每一户的门，会很乱：门卫没法统一检查、你也不知道哪扇门在哪个楼道。**Gateway 就是这个"小区大门 + 门卫总台"**。

- 客户端**只访问 Gateway 一个地址**。
- Gateway 根据请求路径/条件，决定转发给后面哪个微服务。

## 3.2 它到底帮了什么忙（能力清单）

| 能力 | 说明 |
| --- | --- |
| **路由转发** | 收到 `/api/order/**` 就转给订单服务，`/api/stock/**` 转给库存服务 |
| **负载均衡** | 目标服务有多个实例时，帮你在它们之间分配请求 |
| **鉴权** | 进门口先验证 Token / 登录状态，没权限直接挡在外面（不用每个服务都做一遍） |
| **限流** | 防止流量突增打垮后端 |
| **跨域 / 请求/响应处理** | 统一处理跨域、加请求头、日志等 |
| **灰度/过滤** | 通过过滤器实现按比例灰度、参数处理 |

**核心价值：横切关注点（鉴权、限流、跨域、日志）在入口统一做一次，不用每个微服务各写一遍。**

## 3.3 三个核心概念（认出来就不慌）

Gateway 的工作就是围绕这三点：

| 概念 | 通俗理解 | 配置里的样子（示意） |
| --- | --- | --- |
| **Route 路由** | 一条"匹配规则 → 转发到哪"的规则 | `id: order-route`，`uri: lb://order-service` |
| **Predicate 断言** | 什么条件才触发这条路由（路径、Header、时间等） | `Path=/api/order/**` |
| **Filter 过滤器** | 请求转发前后要做的处理（鉴权、加参数、记录） | 全局过滤器 / 路由过滤器 |

```yaml
spring:
  cloud:
    gateway:
      routes:
        - id: order-route
          uri: lb://order-service          # lb:// 表示走 Nacos 负载均衡找到该服务
          predicates:
            - Path=/api/order/**           # Predicate：命中这个路径才转发
          filters:
            - StripPrefix=2                # Filter：去掉前面两层路径前缀
```

## 3.4 Gateway 和 Nginx 的区别（一句话带过）

- **Nginx**：偏"网络流量层面"的转发，适合做反向代理、静态资源、机器级别的负载均衡。
- **Gateway**：微服务层面，能理解"业务路由"（按路径/Header）、能和注册中心联动（`lb://` 动态找服务）、能做微服务鉴权限流。

很多团队会 **Nginx 在最外面挡流量，Gateway 在 Nginx 后面做业务网关**，两者配合，不是二选一。

## 3.5 跟导师讲一句话

`Gateway = 系统的大门+门卫`：所有请求先到它这，它做鉴权、限流、跨域，再按路由把请求转发给背后真正的微服务。

# 第四部分：AI 工具核心概念：Agent / Skill / MCP

> 这一部分帮你把"AI 工具现在都爱讲的那几个词"串清楚。你在目录里已经有一份《AI工具使用教程.md》，那里讲的是具体四个工具**怎么用**；这一部分讲的是它们背后的**概念是什么**。

## 4.1 Agent —— 会"自己干活"的智能体

- **定义**：不只是"你问一句它答一句"的聊天机器人，而是一个**能理解目标、把目标拆成多步、调用工具、观察结果、再调整继续做**的 AI 程序。
- **关键点**：Agent = 规划 + 决策 + 调用工具 + 执行。它能跑一个"流程"，而不是只回一句话。
- **类比**：普通 AI 像"只会背书的顾问"；Agent 像"能自己动手把活干完的实习生"。
- **在你这边**：Codex 就是一个能自主读写代码、跑命令、改文件的 **Agent 环境**。

## 4.2 Skill —— 教 Agent"怎么做"的可复用操作手册

- **定义**：把一套**做事方法/流程/提示词/规范**打包成一个可加载的"技能"。Agent 装上某个 Skill，就学会了用某种方式干活。
- **类比**：Skill = 给 AI 的**岗位 SOP / 操作手册**（`"第一步…第二步…验收…"`）。
- **在你这边**：《AI工具使用教程.md》里讲的 **grill-me / Superpowers / Spec Kit / planning-with-files 全都是 Skill**：
  - `grill-me`：教 Agent 通过一问一答帮你澄清需求；
  - `Superpowers`：教 Agent 一整套从设计→计划→测试→实现→评审的开发流程；
  - `planning-with-files`：教 Agent 用文件记录长任务进度；
  - `Spec Kit`：教 Agent 先写规格/计划/任务再实现。

## 4.3 MCP —— 让 AI 能"接上外部设备"的标准接口

- **定义**：MCP（Model Context Protocol，模型上下文协议）是一种**开放的标准化协议**，让 AI 程序能用统一的方式去连接、操作外部的**工具和数据**（数据库、云文档、Git、文件系统、消息、日历等）。
- **类比**：MCP 像是 AI 的 **"USB/即插即用接口标准"**——只要某个外部系统实现 MCP，AI 就能以同一套姿势调用它，不用每个系统单独做一套对接。
- **价值**：解决"AI 自己只会在对话里想，接不住你公司的数据/系统"的问题。你公司常用工具（飞书、GitLab、MySQL 等）如果暴露为 MCP，Agent 就能直接读写。

## 4.4 三者什么关系？（一个比喻串起来）

```
                     ┌────────────────────────────┐
   Agent（会做事的人）│  用 Skill（工作方法/SOP）   │
                     │  通过 MCP（标准接口）去操作  │
                     │  外部的工具和数据            │
                     └────────────────────────────┘
```

- **Agent** = 一个会自理成事的人（有目标、会拆分、会动手）。
- **Skill** = 他手里那本"怎么做"的操作手册（教方法）。
- **MCP** = 他连接外部设备/系统的标准插头（教连接）。

一句话：**Agent 用 Skill 来做事，通过 MCP 去操作外部系统。**

## 4.5 用你手上的东西把这个概念落地一遍

| 概念 | 在你 ZHGC / MOM 开发里的对应 |
| --- | --- |
| Agent | Codex（你能指挥它写代码、跑命令） |
| Skill | 已经装上的 `planning-with-files`、`grill-me/grilling`、Superpowers 全套、Spec Kit 的 Codex skills（详见《AI工具使用教程.md》） |
| MCP | Agent 未来接入飞书 / GitLab / 数据库等公司系统的"标准接口"（先了解概念，等团队规范再接入） |

## 4.6 导师可能会追问，你可以这样答

| 可能追问 | 参考回答 |
| --- | --- |
| "Skill 和普通提示词有什么区别？" | 普通提示词是消息里临时写一段；Skill 是打包成可复用的规范文件，Agent 一装上、每次都能稳定按同一套方法做。 |
| "MCP 有什么用？" | 让 AI 不用为每个系统各写一套对接，只要系统暴露成 MCP，AI 就能统一读写它（数据库、文档、Git 都能接）。 |
| "你们公司的 AI 工具怎么来的？" | 公司用 ChatGPT 系（明确不让用 Claude 系），我用的是 Codex 环境，装了一批团队允许的 Skill。 |
