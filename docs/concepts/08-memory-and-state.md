# Memory 与状态

## 区分

- 对话历史：本轮或多轮消息记录。
- Agent 状态：任务目标、当前步骤、工具结果、预算和停止原因。
- 持久化业务数据：分析报告、准备计划和用户任务。
- 模型所谓 Memory：将历史或摘要重新注入上下文的应用机制，不等同于模型永久记忆。

## JobCoach 用法

执行状态应由应用拥有并持久化；模型只获得完成当前步骤需要的最小上下文。

## 验证与局限

检查重启恢复、重复请求、状态过期、敏感信息保留和历史摘要失真。记住更多信息会增加隐私和提示注入风险。

## 学习步骤与最小实验

1. 画出一次匹配任务的状态：请求、分析、报告可用、等待确认、任务已保存、失败。
2. 为每个状态记录拥有者、可执行动作、过期时间、重试策略和用户可见文本。
3. 模拟进程在分析中重启、客户端重复提交、保存请求重放和报告过期，检查是否重复副作用。
4. 将对话历史、Agent 运行状态和业务数据分开存储；只向模型注入完成当前步骤所需的最小上下文。
5. 检查删除/保留策略，避免把完整简历、岗位原文和模型日志无限期保存。

实验验收：能在重启后恢复或明确失败，重复请求有幂等行为，状态变化有时间和原因记录。

## 常见误区

- 把数据库里保存的历史称为“模型永久记忆”。
- 将所有历史消息重新拼回 Prompt，导致成本、隐私和提示注入风险失控。
- 没有状态机，靠一个布尔值区分处理中和已完成。

## 复盘问题

1. 哪些状态属于业务事实，哪些只是一次 Agent 运行的临时状态？
2. 用户删除简历后，哪些缓存、日志和向量索引也必须删除？
3. 重试一次是否安全？如何证明它不会重复保存任务？
