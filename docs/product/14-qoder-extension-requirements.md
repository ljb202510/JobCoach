# Qoder-JobCoach 扩展功能需求建议（独立稿）

## 1. 目的与口径

本文是供后续 Trae、Qoder、Codex 三方交叉评审的 **Qoder 独立提案**，不是三方共识或实施承诺。当前 MVP 已能提交岗位与经历文本、查看 Fake/Real 匹配报告及无副作用的准备计划预览；计划保存、历史、RAG、模拟面试等尚未成为产品能力。现状以 [实现边界](11-implementation-boundaries.md) 和实际验证记录为准。

本稿从技术架构与 AI 能力演进的视角出发，关注信息流完整性、系统可扩展性和 AI 工程能力展示面。每条方向含用户故事、第一性原理依据、技术架构价值、依赖、验收要点与权重归属。接口、数据库表与技术选型留到选定单个增量之后设计。

## 2. 从第一性原理推导

### 2.1 核心问题：信息流是单向管道

当前系统的信息流是一条**无反馈、无状态、无积累**的单向管道：

```text
输入（岗位 + 经历）→ 分析（LLM 单次调用）→ 输出（报告 / 计划预览）→ 丢弃
```

这个架构在 MVP 阶段是合理的——它证明了端到端链路可行。但从第一性原理看，它缺少三个关键能力：

1. **持久状态**：每次请求从零开始，无法积累、查询或恢复。
2. **反馈回路**：输出是终点，用户无法基于输出继续行动或验证效果。
3. **外部知识接入**：模型只能依赖自身参数和当前输入，无法引用可信外部资料。

### 2.2 推导公理

- **公理 A1（信息流完整性）**：系统的价值不在于单次输出，而在于信息能流入、积累、被引用、产生行动、反馈回系统。每个拓展方向应补强信息流的某个缺失环节。
- **公理 A2（架构可演进性）**：当前 hexagonal 架构已预留端口（`MatchSessionRepository`、`ExecutionRecorder`），扩展应优先填充已有端口，而非新增抽象层。
- **公理 A3（AI 能力边界可量化）**：每次引入新的 AI 能力（RAG、Agent 对话、工具编排），必须有对照评测证明它比简单方案更好，否则不纳入。
- **公理 A4（双重目标约束）**：每条方向必须能落到 4:4:2 三者之一——作品集产品（4）/ AI coding·概念能力（4）/ Java 后端（2），并说明技术展示价值。
- **公理 A5（边界）**：不自动投递、不抓招聘网站、不做复杂多用户（除非完成隐私评审）；不为展示技术而引入技术。

### 2.3 价值链与信息流映射

```text
              输入层          分析层          行动层          长期使用层
信息流状态：  [流入]    →    [处理]    →    [反馈回路]  →   [状态积累]
当前能力：    文本粘贴       单次 LLM       无              无
缺失能力：    文件解析       来源标注       计划执行跟踪    持久化+历史
             结构化导入     多步推理       练习+反馈       跨会话恢复
                                             ↑
                                    AI 能力层贯穿支撑
                              RAG / Agent / Tool Calling / 评测
```

五层对应本文档第 4 章的方向分组。

## 4. 方向明细

### 输入层

#### Q7 输入减负与结构化解析（P2）

- **用户故事**：作为求职者，我希望上传简历文件而非手工粘贴 2000 字，减少输入摩擦。
- **第一性原理依据**：公理 A1——信息流入的成本越低，系统越容易被使用。当前手工粘贴是最大摩擦点。
- **技术架构价值**：展示文件 I/O 处理、格式校验、结构化输出（从非结构化文本提取结构化经历）。是 hexagonal 架构中 input adapter 的扩展。
- **最小切片**：支持 .txt 纯文本文件上传；提取文本后用户确认编辑再提交分析；解析失败回退手工输入。
- **验收要点**：上传合法文件可解析并进入分析；超大/损坏文件给出明确错误；解析内容不入日志；不经确认不发送或保存。
- **依赖与风险**：先做纯文本，PDF/Word 另行评审；需评估敏感信息处理；不成为 Q1-Q4 的隐含依赖。
- **权重归属**：作品集产品（4）/ Java 后端（2，I/O、校验）。

### 分析层

#### Q2 证据溯源与来源标注（P1）

- **用户故事**：作为求职者，我希望报告中每项判断都能定位到岗位或经历的原文片段，以便核实 AI 没有编造。
- **第一性原理依据**：公理 A1——信息处理环节的输出必须可回溯到输入，否则信息流不可信。公理 A3——可信度是可量化的，来源标注是可验证的。
- **技术架构价值**：展示结构化输出中的来源定位能力；需要模型输出额外的 `sourceRef` 字段并与输入文本对应校验。是 `MatchReport` 契约的增强。
- **最小切片**：报告每项证据附带来源片段引用或明确标注"证据不足"；引用片段必须存在于输入文本中；用户修改经历后可重新分析。
- **验收要点**：脱敏样例覆盖明确具备、明确不具备、只缺证据三种情况；引用片段可定位到输入原文；定位失败时显示"证据不足"而非伪造引用；不编造经历。
- **依赖与风险**：先验证模型能稳定输出来源标注（结构化输出能力）；引用岗位要求与引用个人经历要分开校验；分数变化不能被解释为录用概率。
- **权重归属**：作品集产品（4）/ AI coding（4，结构化输出 + 校验）。

#### Q5 RAG 可信资料检索（P2）

- **用户故事**：作为求职者，我希望技能差距的建议附带可核查的学习资料，以便知道具体去哪里补。
- **第一性原理依据**：公理 A1——信息处理环节可以接入外部知识，而非仅依赖模型参数。公理 A3——RAG 必须证明比无检索更好，否则不引入。
- **技术架构价值**：展示检索增强生成（RAG）实战：资料索引、检索策略、引用注入、结果校验。是 AI 概念文档 `07-rag.md` 的落地。
- **最小切片**：为一项差距生成带资料来源的建议；同时做无检索对照；引用可追溯到具体资料。
- **验收要点**：引用可回溯到来源；有 RAG vs 无 RAG 对照评测记录，效果优于基线；不引入未经评测的资料源；资料引用不能证明用户具备某项技能。
- **依赖与风险**：需确定可信资料源（官方文档 / 面试题库 / 权威教程）；先做关键词检索，向量库为后续；不能仅为展示技术而接入。
- **权重归属**：AI coding（4，RAG 概念落地）。

#### Q8 工具编排扩展（P2）

- **用户故事**：作为系统，我希望在保持白名单与参数校验的前提下，安全地串联多个工具完成复杂任务。
- **第一性原理依据**：公理 A1——信息处理环节可以通过工具链自动化多步操作。公理 A2——当前已有 `PreparationPlanTool`，扩展应复用已有端口。
- **技术架构价值**：展示 function calling 链式调用：工具白名单、参数校验、执行顺序、错误传播。是 `04-tool-calling.md` 概念的深化。
- **最小切片**：新增一个受控工具（如"结构化经历提取"），与现有分析工具串联；白名单和参数校验框架不变。
- **验收要点**：新增工具需白名单注册和参数校验；越权/附加参数被拒；执行有审计记录；不暴露任意 Shell/SQL/文件系统。
- **依赖与风险**：先有 Q3 评测框架验证工具链质量；不成为安全漏洞入口。
- **权重归属**：AI coding（4，Tool Calling 概念深化）。

#### Q9 多模型渠道切换与降级（P2）

- **用户故事**：作为用户，当默认模型不可用或超预算时，我希望系统能切到备选渠道或降级到 Fake，而不是直接失败。
- **第一性原理依据**：公理 A1——信息处理环节的可用性是信息流连续性的前提。公理 A2——当前 `AiGateway` 接口已预留切换能力。
- **技术架构价值**：展示渠道抽象、降级策略、多渠道能力探测。是 `AiGateway` 接口的扩展。
- **最小切片**：主渠道失败可切备选；无备选时可明确降级并提示 Fake 模式；切换不破坏 Fake/Real 回归集。
- **验收要点**：主渠道超时或错误时自动切换；切换过程对用户透明或有明确提示；每个渠道独立验证结构化/工具能力。
- **依赖与风险**：扩展渠道前先逐项验证能力，避免"OpenAI 兼容"假设；需要多个渠道的 API 访问。
- **权重归属**：AI coding（4）/ Java 后端（2，渠道抽象）。

### 行动层

#### Q4 计划确认、保存与执行跟进（P1）

- **用户故事**：作为求职者，我希望确认并保存准备计划后能标记完成状态，以便知道自己还剩什么没做。
- **第一性原理依据**：公理 A1——信息流的反馈回路：输出（计划）→ 行动（执行）→ 反馈（完成状态）→ 系统。没有反馈回路，信息流是断裂的。
- **技术架构价值**：展示受控写入边界和状态管理：用户确认作为写入闸门、幂等键防止重复创建、状态机管理任务进度。是 `PreparationPlan` 域对象的持久化落地。
- **最小切片**：用户显式确认后保存一份计划；支持查询、完成状态标记和删除；未确认不保存。
- **验收要点**：未确认不保存；重复确认不产生重复计划（幂等）；重启后能恢复；删除后不可再查到；失败不会留下"已保存"假状态。
- **依赖与风险**：依赖 Q1 持久化能力；审阅质量应先于保存实施；需先完成隐私决策。
- **权重归属**：作品集产品（4）/ Java 后端（2，受控写入 + 状态管理）。

#### Q6 Agent 式对话分析（P2）

- **用户故事**：作为求职者，我希望针对报告中的某项判断追问细节，以便深入理解差距和改进方向。
- **第一性原理依据**：公理 A1——反馈回路的深度扩展：用户不只是看报告，而是与报告"对话"，信息流从单向变成双向。公理 A3——Agent 对话必须证明比静态报告更有价值。
- **技术架构价值**：展示 Agent loop + 上下文管理：对话状态维护、上下文窗口控制、工具调用（如引用报告内容）、停止条件。是 `05-agent-loop.md` 和 `06-workflow-vs-agent.md` 概念的落地。
- **最小切片**：基于当前报告上下文，支持 1-3 轮追问；每轮回答引用报告内容；不脱离上下文。
- **验收要点**：追问不脱离当前报告上下文；回答可追溯到报告中的具体判断；不产生幻觉或矛盾信息；有明确结束条件。
- **依赖与风险**：基础报告闭环（Q1/Q2/Q4）完成后才启动；对话系统成本高，"幻觉"风险大；需可回溯评价。
- **权重归属**：AI coding（4，Agent loop + 上下文管理）。

### 长期使用层

#### Q1 持久化层与数据生命周期（P1）

- **用户故事**：作为求职者，我希望重启后能看到之前的报告和计划，以便跨天跟进准备进度。
- **第一性原理依据**：公理 A1——信息流必须有状态积累环节，否则每次从零开始，无法支撑长期使用。公理 A2——当前 `MatchSessionRepository` 和 `ExecutionRecorder` 端口已定义但未实现，扩展应填充已有端口。
- **技术架构价值**：展示关系建模、迁移管理、Repository 模式、数据完整性保障。是 hexagonal 架构中 persistence adapter 的落地，补全架构的最后一块拼图。
- **最小切片**：MySQL 存储报告与计划；Flyway 迁移脚本可重复执行；支持查询、删除；服务重启后数据可恢复。
- **验收要点**：迁移脚本幂等执行；集成测试覆盖写入、查询、删除；删除后不可再查到；敏感数据不写入日志；日志仅脱敏摘要。
- **依赖与风险**：需先完成隐私决策（保留期限、删除策略、是否需身份隔离）；先升级 `05-domain-model` 草图为正式 schema。
- **权重归属**：作品集产品（4）/ Java 后端（2，持久化 + 迁移 + Repository）。

### 贯穿层

#### Q3 评测基准框架（P1）

- **用户故事**：作为开发者，我需要一个固定测试集和评分规则，以便比较不同模型、prompt 或 AI 能力的质量变化。
- **第一性原理依据**：公理 A3——任何 AI 能力扩展必须有对照评测，否则无法判断它是"更好"还是"只是不同"。评测是所有 AI 功能拓展的前提。
- **技术架构价值**：展示 AI 工程严谨性：固定测试集、评分规则、自动化回归、失败分类、结果可复现。不是"跑通就行"，而是可量化比较。
- **最小切片**：3-5 个脱敏固定输入样例 + 预期输出结构 + 自动化通过率统计；每次模型或 prompt 变更后自动运行。
- **验收要点**：记录通过率、失败类别和分数偏差；结果可复现；不含密钥或真实简历；新增改动可跑回归。
- **依赖与风险**：需先有稳定的 Real gateway 和脱敏样例；先小后大，不追求学术级评测。
- **权重归属**：AI coding（4，评测工程）。

#### Q10 可观测性与成本记录（P2）

- **用户故事**：作为开发者，我希望追踪每次调用的耗时、成本与失败类别，以便优化与复盘。
- **第一性原理依据**：公理 A1——贯穿层的信息度量：信息流的每个环节都应可追踪、可度量。公理 A3——Q3 评测框架的补充，从离线评测扩展到在线度量。
- **技术架构价值**：展示执行追踪、成本分析、脱敏摘要。是 `ExecutionRecorder` 端口的扩展。
- **最小切片**：每次调用记录耗时、模型、token 消耗和失败类别；脱敏摘要入日志；成本可统计。
- **验收要点**：每次调用能解释耗时与失败原因；成本可统计；不记录敏感原文；与 Q3 评测互补。
- **依赖与风险**：与 Q3 评测互补，先做记录后做指标面板。
- **权重归属**：AI coding（4）/ Java 后端（2，度量能力）。

## 5. 优先级排序与依赖关系

```text
Q3 评测基准 ──────────────────────────────────┐
Q1 持久化 ──→ Q4 计划保存与跟进 ──────────────┤
Q2 证据溯源 ──────────────────────────────────┤
                                              ├──→ Q5 RAG（需 Q3 评测）
                                              ├──→ Q6 Agent 对话（需 Q2+Q4）
                                              ├──→ Q7 输入减负
                                              ├──→ Q8 工具编排（需 Q3）
                                              ├──→ Q9 渠道切换
                                              └──→ Q10 可观测性
```

**建议实施顺序**：

1. **Q3 评测基准**（P1）：先建度量能力，后续每次变更都可量化比较。
2. **Q1 持久化**（P1）：打通数据层，补全 hexagonal 架构。
3. **Q2 证据溯源**（P1）：补强报告可信度。
4. **Q4 计划保存**（P1）：完成反馈回路闭环。
5. **Q5/Q6/Q7/Q8/Q9/Q10**（P2）：按用户反馈和技术展示需求选择。

**理由**：先有评测（Q3）→ 再做持久化（Q1）→ 然后补强可信度（Q2）和闭环（Q4）→ 最后按用户痛点选择拓展。这个顺序确保每一步都有度量支撑，且不阻塞后续扩展。

## 6. 与其他提案的差异

与 Trae（12）和 Codex（13）的提案相比，本稿的独特视角：

- **信息流完整性**：从"信息如何流入、处理、反馈、积累"的角度推导，而非单纯列举功能。
- **架构端口填充**：优先填充已有端口（`MatchSessionRepository`、`ExecutionRecorder`、`AiGateway`），而非新增抽象层。
- **评测先于接入**：强调任何新 AI 能力（RAG、Agent、工具链）必须有对照评测，不做技术装饰。
- **可观测性**：独立提出 Q10 在线度量，与 Q3 离线评测互补。
