# 五天学习与交付总计划

项目：AI 求职教练系统（JobCoach）。输入岗位描述和个人经历，输出结构化匹配分析、技能差距和准备任务；五天 MVP 先完成不持久化的 Fake 闭环，后续通过受控工具保存任务计划并记录执行过程。

技术基线：Java 21、Spring Boot、LangChain4j、Spring RestClient、MyBatis-Plus、MySQL、Vue 3、TypeScript、Vite、Docker Compose。具体依赖版本在官方兼容性核验后确定。

## 每天固定结构

每一天都围绕 JobCoach 的一轮真实 AI coding 迭代展开：需求评审/拆解、实现、Review、测试、联调、复盘和下一轮计划。概念学习不单独排成脱离项目的课程，而是在当前迭代需要时引入 Prompt、RAG、Skill、Tool Calling、MCP、Agent 等能力。完成代码不等于完成当天任务，必须同时留下过程证据和可解释结论。

## 时间分配原则

按 4:4:2 分配精力：约 40% 用于 AI coding 主线中的 JobCoach MVP 功能交付，约 40% 用于同一开发过程中的 AI 概念、Codex、Skills、工具和验证能力，约 20% 用于支撑当前功能所需的 Java 后端。每天的任务块会标注它在同一条交付链中的位置，而不是把三类内容做成互不相关的课程。

AI coding 全流程包括：检查现状、准备上下文、拆解任务、提出方案、限定改动、实施小步变更、运行测试、阅读错误、查看 diff、Review、记录决策和复盘。

## 路线

| 天数 | 任务 | 验收 |
|---|---|---|
| 1 | 评审 JobCoach 需求并建立 AI coding 工作方式 | 形成 MVP 优先级、模块拆分、验收标准和第一轮实施计划 |
| 2 | 第一轮敏捷迭代：Fake 后端主链路 | 完成可测试的岗位匹配 API，并留下探索、方案、编码、测试和 Review 证据 |
| 3 | 第二轮敏捷迭代：真实 AI 能力与受控工具 | 在真实功能中引入结构化输出、Tool Calling、Workflow/Agent，并明确失败降级 |
| 4 | 第三轮敏捷迭代：Vue 联调与 RAG 评估 | 完成可操作端到端 MVP，验证 UI、API、模型错误和检索收益 |
| 5 | 交付迭代：整体 Review、回归和敏捷复盘 | 形成完整 JobCoach 项目、可复现 README、演示材料和下一轮 backlog |

## 优先级

- P0：岗位+经历分析主流程、Fake 受控边界、Vue 页面、测试、README；五天 MVP 不持久化。
- P1：MySQL 持久化、渠道切换、流式输出、规则检索和最小 RAG。
- P2：Redis、向量数据库、多 Agent、登录、异步任务和部署。

## 每日执行协议

每天开始前先完成四项准备：

1. 读取 `PROJECT_GOALS.md`、当天任务和上一天 `progress.md`，确认目标没有漂移。
2. 运行与当天相关的基线命令，记录代码和文档当前状态；已有失败先处理或明确隔离。
3. 把当天任务拆成最多 5 个可验证小循环，每个循环写出文件范围、产出物和最快检查。
4. 提前标出需要用户确认的产品、隐私、权限和不可逆副作用，不在无人确认时猜测。

每个小循环都遵循：

```text
阅读证据 -> 写计划 -> 小步执行 -> 最快验证 -> 查看 diff/结果 -> 记录结论
```

## 五天证据矩阵

| 天数 | 作品证据 | AI/Codex 证据 | Java 证据 | 必须回答的问题 |
|---|---|---|---|---|
| 1 | MVP 优先级、模块边界、验收标准 | 需求评审、任务拆分、Codex 工作区/Plan | API 和分层草案 | 这一轮最有价值的 P0 是什么？ |
| 2 | Fake 主链路 | 上下文准备、计划、实现、单测、Review | DTO、用例、错误 | 代码是否满足需求而非只通过编译？ |
| 3 | 真实模型/工具增量 | 能力探测、Skill/Tool/Agent 使用记录 | adapter、权限、执行状态 | 模型失败时 MVP 如何继续？ |
| 4 | 前后端端到端链路 | 联调、RAG 对照、UI 检查 | HTTP、错误、回归 | 用户实际能否完成任务？ |
| 5 | 完整 MVP 交付 | 总结完整 AI coding 流程和下一轮敏捷方法 | 构建、测试、配置、文档 | 哪些已验证，下一轮先做什么？ |

## 每日结束门禁

- 产出文件已落盘，聊天中的结论已同步到文档。
- 命令、退出码、覆盖范围和未覆盖风险已记录。
- 事实、用户确认、草案、待验证和暂缓没有混写。
- 未完成项有下一步和阻塞原因，不用“差不多完成”掩盖。
- 只有完成当天验收并记录复盘，才进入下一天；不以时间耗尽作为完成标准。
